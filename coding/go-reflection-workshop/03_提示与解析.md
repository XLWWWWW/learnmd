# 提示、答案与参考设计

建议先在题册写预测、再运行。不要一开始就打开完整参考实现。下面把提示折叠起来；如果当前查看器不支持折叠，可以先停在对应题目之前。

## A. 输出推演答案

### Q01

```text
false
true
int64
```

定义类型具有自己的类型身份；别名没有产生新的类型。Kind 只能表达类别，不能证明类型相同或可赋值，例如两个不同定义类型即使同为 Int64 也不能直接互相赋值。

### Q02

```text
*bytes.Buffer
io.Writer
interface
```

TypeOf 看接口承载的动态类型；TypeFor 看写出的类型参数；对 `&w` 解引用得到接口变量位置。旧写法是 `reflect.TypeOf((*io.Writer)(nil)).Elem()`：先构造接口指针的 Type，再取元素类型。

### Q03

```text
false false true
20
```

只有 c 代表 x 的可写位置。a 和 b 的 SetInt 都会 panic：a 不可设置；b 既不可设置，Kind 还是 Pointer，不满足 SetInt 所需的整数 Kind。

### Q04

```text
true false false
7
```

字段所在对象可寻址，字段本身可以取地址；未导出字段仍不能普通反射 Set 或 Interface。`Int()` 可以读取该整数，这不等于所有暴露接口都开放。额外的 `Interface()` 调用会 panic。

### Q05

```text
false true true
false
```

接口承载 `*int` 动态类型及 nil 指针值，因此不是 nil 接口。ValueOf(nil) 则没有值。对前者调用 IsNil 有意义；对无效 Value 或 Int Kind 调用 IsNil 都不符合前置条件。

### Q06

```text
true
false
true
false
```

slice 的类型零值是 nil slice，不是每一个长度为零的 slice。Zero 创建的是“某个类型的零值”，Value 自身的零值表示“没有反射值”。显式 false 也属于 bool 零值，若用零值推断未填写，会错误覆盖用户的选择。

### Q07

```text
false
true
false
true
```

slice 共享底层数组，元素可寻址；按值传入的数组元素不可设置。Append 返回新的 slice 头部，即使没有扩容也应保存返回值。若要写回调用者变量：

```go
sv := reflect.ValueOf(&s).Elem()
sv.Set(reflect.Append(sv, reflect.ValueOf(2)))
```

这会更新 s 的长度、容量和数据指针所组成的 slice 值。修改元素与替换 slice 变量是不同操作。

### Q08

```text
false false
0 false
```

map 条目不能直接寻址，所以 MapIndex 返回值不可设置；map 仍支持用 SetMapIndex 更新条目。无效 Value 表示删除；`reflect.Zero(v.Type().Elem())` 表示写入元素零值，保留该键。nil map 可以查找、删除，但不能插入值；E09 为了统一输入协议直接拒绝 nil map。

### Q09

```text
false
true
1
```

合法整数转换允许截断，并不保证无损。要无损写入，可以创建目标类型的可写 Value，用 OverflowInt 检查后才 SetInt。若还有加法，要先防止在 int64 求和时就已经溢出。

### Q10

```text
true
false
```

slice 到数组的转换在类型层面允许，但长度 1 不足以填入长度 2 的数组，直接 Convert 会 panic。长度改成 2 后 CanConvert 为 true，转换得到一个数组值。

### Q11

```text
false
true 1
2
```

Add 属于 `*Counter` 的方法集。Value 的方法值已经绑定接收者，只剩一个 int 参数。`Type.Method` 的 Method.Func 是带显式接收者参数的函数形式，调用时要按照其完整签名传入接收者。

### Q12

```text
false
false
false
```

nil slice 与非 nil 空 slice 不深度相等；动态类型不同不深度相等；非 nil 函数不因指向同一个函数而深度相等。比较时间点常用 `a.Equal(b)`，比较 JSON 语义或业务对象应先明确规范化和相等协议。

## B. 修复题解析

### Q13：先定义“空”

可用反例：nil 接口、0、struct{}{} 都会因为不满足 IsNil 前提而 panic；非 nil 空 slice 返回 false，而很多人以为 Empty 会返回 true，这又是命名与语义不一致。

如果需求只是 nil，可重命名为 `IsNilLike`：先检查 IsValid，无效则 true；再 switch 六种常见可为 nil 的 Kind；这些 Kind 调用 IsNil，其余返回 false。nil → true，0 → false，非 nil 空 slice → false。完整代码见 E02。

如果需求是“未提供”，则应在数据协议里记录是否提供；如果需求是“长度为零”，那是另一组适用 Kind 与函数名字。

### Q14：输入与标签协议都缺失

至少有这些问题：

1. nil 输入无效，调用 NumField 不成立。
2. 指针需要检查 nil 并解引用。
3. 非 struct 输入不能 NumField。
4. 未导出字段 Interface 会 panic。
5. 无标签字段都使用空 key，造成覆盖。
6. `json:"-"` 没有被跳过。
7. `json:"name,omitempty"` 被整个当成 key。
8. 重名标签静默覆盖数据。
9. omitempty 的语义未定义，嵌入字段与浅层/递归也没定义。

先声明“只做直接字段的浅层映射，默认字段名、明确重命名与跳过、遇冲突报错”，再写实现。E05 使用自定义 map 标签，避免宣称复刻标准 JSON。

### Q15：SetInt 不代替无损检查

输出为 `-128`。128 写入 int8 后低 8 位是 `10000000`，对应有符号 int8 的 -128。

下面是只处理已知 int8 类型的修复，先把问题做清楚再推广：

```go
func SetInt8(dst *int8, n int64) error {
    if dst == nil {
        return fmt.Errorf("nil destination")
    }
    v := reflect.ValueOf(dst).Elem()
    if v.OverflowInt(n) {
        return fmt.Errorf("%d overflows int8", n)
    }
    v.SetInt(n)
    return nil
}
```

-129 和 128 返回错误且不写入；-128 和 127 成功。推广到任意有符号整数时，再检查目标有效性、指针、整数 Kind 和 CanSet。

### Q16：先改副本，再写回

MapIndex 得到的结构体不是可设置的存储位置。已知 `map[string]User` 的直接写法更简单：

```go
u, ok := m["u1"]
if !ok {
    return fmt.Errorf("user not found")
}
u.Name = "after"
m["u1"] = u
```

如果确实需要在未知结构体类型上反射操作，可以创建相同类型的可写副本：

```go
mv := reflect.ValueOf(m)
key := reflect.ValueOf("u1")
old := mv.MapIndex(key)
if !old.IsValid() {
    return fmt.Errorf("user not found")
}
copyValue := reflect.New(old.Type()).Elem()
copyValue.Set(old)
copyValue.FieldByName("Name").SetString("after")
mv.SetMapIndex(key, copyValue)
```

上面按本题已知的 User 类型写；通用版本还要验证字段存在、类型与可设置性。若改用 `map[string]*User`，需要检查键与指针是否存在，之后可修改其指向的结构体。并发时既要保护 map 访问，也要保护共享 User 的读写；使用指针不自动获得同步。

### Q17：类型元数据与对象值不能混用

被缓存的 Value 始终绑定第一次请求中的 user.Name。第二次相同类型请求命中缓存后，仍然修改第一个用户。加锁最多让这个错误串行发生，不能让 Value 自动绑定第二个对象。

正确缓存：字段名、字段下标或访问路径、字段 Type、解析后的标签与规则。每次调用重新从当前对象构造 Value，再沿缓存路径取字段。缓存路径若包含切片，应避免外部修改；可以不暴露，或复制后返回。

缓存并发访问需要同步；共享业务值的并发访问单独同步。持有对象 Value 还可能延长原对象生命周期，让缓存意外保留大量请求数据。

### Q18：异常不全是参数错误

应该区分：

- 注册/调用协议错误：非函数、nil 函数、变参策略不支持、参数数量错误。
- 参数赋值错误：具体值不可赋给目标类型、nil 不适合标量参数。
- 业务返回值：函数正常返回的 error，不是调用器错误。
- 业务 panic：业务代码缺陷或主动 panic，按本题协议继续传播。

先检查 Value 有效性与 Func Kind，再检查 IsNil、签名、参数和赋值规则。无类型 nil 参数不能直接变成 ValueOf(nil) 传入，应按目标可为 nil 类型创建 `reflect.Zero(parameterType)`。

入口 recover 可按产品需求单独设计，但应准确标注内部异常，不能把所有 panic 都写成 bad arguments。E08 不做这种混淆。

## C. 编程题：先看提示，再看思路

### E01 Inspect

<details>
<summary>提示</summary>

先调用 TypeOf。Type 为 nil 时不能调用它的 Kind 方法。

</details>

参考思路：nil 单独返回；其余返回 Type 及其 Kind。不要以字符串反推 Kind，也不要把定义类型替换成内置类型。

### E02 IsNilLike

<details>
<summary>提示</summary>

IsValid 先于 IsNil。switch 中只列本题承诺的六种 Kind。

</details>

参考思路：无效值是 nil 接口；有效且可为 nil 的值用 IsNil；其他全部 false。不用 recover 实现正常分支。

### E03 Fields

<details>
<summary>提示</summary>

统一输入到 struct Value，然后遍历它的 Type。Tag.Lookup 返回两个值。

</details>

参考思路：最多解一层非 nil 指针，验证 Struct；按直接字段顺序收集导出字段。Index 保存原结构体下标，不能因跳过未导出字段而重新编号。返回原始 json 标签，不解析其选项。

### E04 SetField

<details>
<summary>提示</summary>

题目只支持直接字段。找到字段后先 CanSet，再把源值按目标 Type 检查；无类型 nil 需要单独处理。

</details>

参考思路：验证非 nil `*struct`，遍历直接字段查名；导出性与 CanSet 都通过后，根据 AssignableTo 赋值。无类型 nil 用目标类型的 Zero，不把零 Value 传给 Set。接口赋值检查类型是否实现接口，而不是只看 Type 相等。

### E05 ToMap

<details>
<summary>提示</summary>

标签按逗号拆出名字与选项；输出 key 的“已出现集合”应独立于已经输出的数据。

</details>

参考思路：先做字段名解析、选项验证和重复名检查，再根据 IsZero 决定是否省略。否则两个重复字段都恰巧是零值时，错误的 schema 会被隐藏。通过 CanInterface 后提取值；不深拷贝内部引用。

### E06 ApplyDefaults

<details>
<summary>提示</summary>

不要一边解析一边修改目标。先为每个待写字段创建同类型的临时 Value，并记录字段下标。

</details>

参考思路：只处理带标签的导出零值字段。string 直接 SetString；bool 使用 ParseBool；有符号整数使用 `ParseInt(raw, 10, fieldType.Bits())`。使用字段原类型创建临时值，可以保留定义类型身份。全部成功后提交。

非零字段即使 default 标签格式不合法，本题也不解析；这属于题目协议。如果生产环境希望在启动时验证所有标签，应把 schema 验证独立出来。

### E07 Validate

<details>
<summary>提示</summary>

“业务违规”与“规则格式错误”是两种返回通道。规则顺序和字段顺序都要保留。

</details>

参考思路：required 对 IsZero 做判断；min 先解析阈值，再分派字符串与整数。字符串使用 utf8.RuneCountInString，不使用字节长度。rune 是 Unicode 码点，不保证等于用户感知的字素簇数量，复杂 emoji 或组合字符需要更明确的产品定义。

遇到 schema 错误立即返回 error，并丢弃已收集业务违规。required 对 false、0 返回违规，对非 nil 空 slice 不违规；这些是本题的 Go 零值协议，业务模型可以选择别的规则。

### E08 Invoke

<details>
<summary>提示</summary>

先完整检查所有参数，再执行 Call。可以与 E04 共用“任意值转成可赋给目标 Type 的 Value”的辅助函数。

</details>

参考思路：检查有效 Func、非 nil、非变参、NumIn；按每个 In(i) 构造参数。Call 后把所有结果 Interface 回普通值。不要把结果中的 error 提升成调用器 error；也不要吞掉业务 panic。

若扩展为变参，建议给出明确入口，例如分别提供 `Invoke` 与 `InvokeSlice`，而非依据最后一个参数是不是 slice 来猜测用户意图。

### E09 IncrementMap

<details>
<summary>提示</summary>

MapIndex 的结果不能 Set。创建元素类型的可写临时 Value，再 SetMapIndex。还要检查 int64 求和在目标位宽检查之前有没有溢出。

</details>

设原值为 a、增量为 d：

- d > 0 且 a > MaxInt64 - d，求和溢出。
- d < 0 且 a < MinInt64 - d，求和溢出。
- 其余情况下 a+d 可以在 int64 中安全计算，再对目标 Value 做 OverflowInt。

缺失键使用 0；键的 Kind 已证明是 String，因此可将普通 string 明确 Convert 为定义的字符串键类型。这里的转换被输入协议证明合法，和对所有输入盲目 Convert 不同。

### E10 FieldCache

<details>
<summary>提示</summary>

sync.Map 的 LoadOrStore 允许并发构建后统一保存。结果切片应复制；当前 FieldInfo 内都是不可变字段，没有嵌套可变切片。

</details>

参考思路：把 `*T` 规范化为 T，验证 Struct；命中缓存时复制结果，未命中时构建、LoadOrStore，再复制最终存储值。避免复制已经使用过的 FieldCache，因为里面有同步原语。

这里允许并发重复构建，换取简单实现。若构建昂贵且必须只执行一次，可另用每个类型的 once / promise 结构，但仍要仔细处理构建错误。

### E11 ScanRow

<details>
<summary>提示</summary>

需要两个检查集合：schema 中的 db 名是否重复、输入 columns 是否重复。值检查成功后暂存，最后提交。

</details>

参考思路：验证目标与数量；从导出字段构建列名到下标的映射；依次检查列名与源值可赋值性；把每次写入记录为 `{index, value}`；全部通过后才 Set。

int64 与 int 即使当前值都能装下，也不能按本题协议自动转换。nil 到指针可表示 SQL NULL 的一种简化形式，但真实扫描器还需要 Scanner 和驱动值转换规则。本题的原子性只指失败时不写入，没有跨 goroutine 同步语义。

### E12 性能实验

<details>
<summary>提示</summary>

看耗时的同时看分配。思考 benchmark 热循环是否包含标签解析、构造对象和业务处理。

</details>

参考答案的关键点：

1. 按名读取包含名字查找与字段解析；下标读取已经知道目标位置。二者都还有运行时反射操作。
2. 防御性复制返回切片，避免调用者污染缓存，仍可能分配。性能取舍必须与 API 所承诺的隔离一起讨论。
3. 亚纳秒结果是经过编译器优化的循环平均值，不能理解成某个函数的绝对调用延迟，更不能换算成请求吞吐量。
4. 原总成本记为 1，新成本为 `0.99 + 0.01/10 = 0.991`；整体加速约 `1/0.991 = 1.0091` 倍，即约 0.9%。
5. 端到端 benchmark 应使用相同输入、同样错误检查、同样对象生命周期，对比直接实现、反射实现、缓存实现；冷启动和热路径分开测。

本次实测结果见 `04_验证记录.md`，它是特定机器与版本上的样本，不是要求你达到的标准。

## D. 综合项目参考设计与评分

### P01 审计导出器

推荐分两层：类型分析得到字段白名单、输出名和策略；值遍历针对当前输入生成新结果。进入嵌套对象时维护路径与深度，错误例如 `User.Manager.Next: cycle detected`。

本题只递归 struct / `*struct` 及其 slice，可以在当前递归路径上用可比较的指针接口值记录已进入对象。离开节点时删除记录。这比永久记录“见过的对象”更准确：共享引用是有向无环图的一部分，并不一定是循环。

先读取标签决定是否跳过或脱敏，再决定是否需要深入值；脱敏字段只返回 `"***"`，不必递归其中的对象。结果对象均重新创建。标量字符串等值可直接返回，不支持的集合类型显式报错。

建议验收用例：未标记字段、未导出字段、重名标签、未知选项、nil 嵌套指针、自引用、两个字段指向同一对象、恰好达到与超过深度限制、空 slice、切片内循环、输入未修改。

### P02 请求绑定器

推荐流程：解析类型白名单 → 验证未知 key 与重复规则 → 在全新临时值上解析所有输入 → 校验全部待写值 → 提交。

缺失与零值通过 params 是否有 key 区分。对指针字段分配新目标，再解析，不通过原字段指针修改已有对象；对 []string 复制参数切片。自定义 TextUnmarshaler 也在新建的值上调用，失败就丢弃该临时值。

若引入整对象校验，DTO 可以在临时副本上组装，但浅拷贝不代表嵌套指针被复制。当前范围下应保证所有被绑定的引用值都独立创建，禁止解析器就地修改原引用对象。

建议用例：缺失 key 保留值、显式 false、显式 0、空字符串、重复 scalar 参数、[]string 多值与拷贝隔离、int8 溢出、typed nil 目标、未知 key、未允许字段、自定义解析失败后原对象不变。

### P03 动态处理器注册表

注册时验证固定签名、context 与 error 的准确类型，以及请求和响应的 Struct Kind。保存只读 adapter：函数 Value、请求 Type、响应 Type。不保存每次请求的 Value。

Dispatch 拿读锁找到 adapter，释放锁；检查 ctx；创建独立请求值；使用 json.Unmarshal；Call；读取业务 error；成功才 Marshal 响应。注册写锁只保护表，不覆盖业务调用，避免慢处理器阻塞其他注册或分发。

返回值的声明类型已经保证是 error 接口，可以对该反射结果调用 IsNil 判断接口本身是否 nil。带类型的 nil 指针装在 error 中仍是非 nil error，应该保持原有 Go 语义。

context 取消前的检查只能避免已取消请求开始执行，执行中的处理器还必须主动遵守 context。若产品需要 panic 边界，可在最外层设计单独的内部错误处理策略，不与输入错误混为一谈。

建议用例：nil 函数、错误参数数目、错误 context 类型、第二返回值是具体 error 实现而非 error 接口、重复名称、未知名称、无效 JSON、成功结果、业务 error、typed nil error、业务 panic、取消 context、并发注册与分发、多个请求对象隔离。

### 自评标准

| 维度 | 权重 | 要求 |
|---|---:|---|
| 行为正确 | 35% | 正常输入与边界输入符合自己声明的协议 |
| 错误可诊断 | 20% | 能定位字段 / 参数，区分 schema 错误与业务违规 |
| 状态与并发 | 20% | 失败不留半更新，缓存与对象状态责任清楚 |
| 设计解释 | 15% | 能说明为何需要反射，是否有接口或静态替代方案 |
| 性能证据 | 10% | benchmark 可复现，结论不超出测量范围 |

如果一段实现“能跑”，但你不能解释它遇到 nil、多层指针、定义类型或循环引用时会发生什么，继续补充协议与反例，比背更多 API 更有帮助。
