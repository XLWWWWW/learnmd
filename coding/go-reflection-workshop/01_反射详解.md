# Go 反射详解：从运行时类型到可维护的通用组件

## 1. 反射重要在哪里

你说它很重要，这个方向是对的，不过它在不同工作里的出现频率不同。

写订单处理时，你通常知道自己拿到的是 `Order`，可以直接访问 `order.ID`。写一个能处理用户任意结构体的编码器时，你事先不知道字段名、字段类型、字段上的标签，也不能要求所有用户都给自己的结构体增加同一个方法。这时就需要程序在运行时查看类型的结构，并决定如何读取或写入。

可以把反射理解成：**程序运行时，对已经存在的类型和值进行检查、构造和操作。** 它不会把 Go 变成能任意执行字符串代码的语言，也不能给现有类型补上新方法。

官方对接口与反射的介绍见 [The Laws of Reflection](https://go.dev/blog/laws-of-reflection)。下面的代码均为本材料编写，可通过 `concepts` 包核对实际输出。

三个值得掌握的层次：

- 使用库：理解为什么 `json.Unmarshal` 需要传指针、标签为什么有效、哪些字段会被忽略。
- 读库源码：能看懂 `Kind` 分派、字段遍历、接口扩展点和类型缓存。
- 写通用组件：能明确输入协议，并把类型错误、nil、溢出和并发问题变成可控行为。

学习目标不是让业务代码处处使用反射，而是到第三层时仍能解释每一次反射操作为什么成立。

## 2. `Type`、`Kind`、`Value` 分别解决什么问题

| 概念 | 回答的问题 | 例子 |
|---|---|---|
| `reflect.Type` | 它的准确类型是什么？ | `UserID`、`int64`、`*User`、`[]User` |
| `reflect.Kind` | 它属于哪类表示形式？ | `Int64`、`Pointer`、`Slice`、`Struct` |
| `reflect.Value` | 具体值是什么？允许怎样读写？ | 读取整数、访问字段、设置元素、调用函数 |

```go
type UserID int64

id := UserID(7)
t := reflect.TypeOf(id)
v := reflect.ValueOf(id)

fmt.Println(t == reflect.TypeOf(int64(0))) // false
fmt.Println(t.Kind() == reflect.Int64)    // true
fmt.Println(v.Int())                     // 7，返回值类型为 int64
```

`UserID` 和 `int64` 的 Kind 相同，但它们不是相同类型。因此，一个按 Kind 编写的整数读取器可以理解它们；一个严格赋值器仍须检查是否可以赋值。

`type Alias = int64` 则是类型别名，没有定义新的类型，别把它和 `type UserID int64` 混在一起。

实用判断：**按 Kind 决定调用哪组 API，按 Type 判断类型身份、赋值关系和接口实现。** 不要把 `Type.String()` 当唯一类型标识；类型缓存直接使用 `reflect.Type` 作为键。

## 3. 接口为什么与反射紧密相关

把接口看成“动态类型 + 动态值”这个二元组，有助于理解反射；这是学习模型，不需要依赖接口的内存布局。

```go
var x any = int64(7)

fmt.Println(reflect.TypeOf(x))                        // int64
fmt.Println(reflect.ValueOf(&x).Elem().Kind())        // interface
fmt.Println(reflect.ValueOf(&x).Elem().Elem().Kind()) // int64
```

第一行传入接口所承载的具体值，因而看到动态类型。第二行先拿到接口变量的地址，再解引用，因而得到接口变量本身。第三行再解开接口包装，才看到内部整数。

由此可以理解经典的三条反射定律：

1. 普通值通过接口参数进入 `TypeOf` / `ValueOf`，变成反射对象。
2. 合法且允许暴露的 `Value` 可以通过 `Interface()` 回到普通 Go 值。
3. 想通过反射改变某个存储位置，需要该位置可设置。

`Interface()` 的返回类型是 `any`，不是自动恢复某个静态类型：

```go
v := reflect.ValueOf(int64(7))
n, ok := v.Interface().(int64)
fmt.Println(n, ok) // 7 true
```

如果只是判断某个已知接口是否实现，一般直接写类型断言：

```go
if s, ok := x.(fmt.Stringer); ok {
    fmt.Println(s.String())
}
```

这比先反射找 `String` 方法更清晰。

Go 1.22 起，已知类型参数可用 `reflect.TypeFor[T]()` 获取类型。例如 `reflect.TypeFor[io.Writer]()` 能拿到接口类型；而 `reflect.TypeOf(w)` 看的是 `w` 所承载的动态类型。API 版本与定义见 [Go 1.22 reflect 文档](https://pkg.go.dev/reflect@go1.22.0#TypeFor)。

## 4. nil、无效 Value、类型零值：先分清再调用

这是最容易出 panic 的区域。

| 表达式或状态 | `IsValid()` | `Kind()` | 应如何理解 |
|---|---:|---|---|
| `reflect.ValueOf(nil)` | false | Invalid | 没有承载值 |
| `reflect.Value{}` | false | Invalid | Value 自身的零值，表示无效 |
| `reflect.ValueOf((*int)(nil))` | true | Pointer | 有类型的 nil 指针 |
| `reflect.Zero(reflect.TypeOf(0))` | true | Int | 有效的 int 值 0 |
| 找不到字段或 map 键得到的 Value | false | Invalid | 查找没有结果，具体 API 需看返回协议 |

再看“带类型的 nil”：

```go
var p *int
var x any = p

fmt.Println(x == nil)                       // false
fmt.Println(reflect.ValueOf(x).IsValid())    // true
fmt.Println(reflect.ValueOf(x).IsNil())      // true
```

`x` 已经承载 `*int` 类型，不是 nil 接口。这个现象同样会发生在 `error` 返回值中，官方解释见 [FAQ：nil error 为什么不等于 nil](https://go.dev/doc/faq#nil_error)。没有错误时应明确返回 `nil`，不要用反射掩盖错误的返回逻辑。

三个判断的用途不同：

- `IsValid`：是否有一个反射值。先用它保护后面的 `Type`、`Interface`、`IsZero` 等操作。
- `IsNil`：当前有效值是否为 nil；本材料对 Channel、Func、Interface、Map、Pointer、Slice 六种 Kind 使用它。不能对 int 或 struct 直接调用。
- `IsZero`：是否等于当前类型的零值。它不是通用的“业务为空”定义。

例如 `[]int(nil)` 是 slice 零值，`[]int{}` 是非 nil 的空 slice，因此后者 `IsZero()` 为 false。`false` 和 `0` 都是零值，却可能是用户有意填写的有效值。

一个可靠的 nil 判断函数先检查有效性，再分派 Kind；E02 就是在练这个协议。不要写成 `reflect.ValueOf(x).IsNil()` 一行覆盖所有输入。

## 5. 为什么传了指针，还要 `.Elem()`

```go
x := 10
v1 := reflect.ValueOf(x)
v2 := reflect.ValueOf(&x)
v3 := v2.Elem()

fmt.Println(v1.CanSet()) // false：拿到的是按值传入的整数
fmt.Println(v2.CanSet()) // false：指针这个值本身不是可设置位置
fmt.Println(v3.CanSet()) // true：指向 x 的存储位置
v3.SetInt(20)
fmt.Println(x)           // 20
```

“拿到了一个地址”不等于“当前 Value 代表的就是需要修改的位置”。`Elem()` 在这里相当于解引用。

`Elem()` 有两种常用含义：对指针取指向的值，对接口取承载的具体值。不要对 struct 或整数随手调用它。nil 指针解引用后的反射值会无效，应先检查。

### 可寻址、可设置、可暴露分别判断

| API | 关心的问题 |
|---|---|
| `CanAddr()` | 可以对这个值取地址吗？ |
| `CanSet()` | 可以替换这个位置存的值吗？ |
| `CanInterface()` | 可以通过 `Interface()` 暴露这个值吗？ |

未导出字段能说明它们并不等价：

```go
u := struct{ secret int }{secret: 7}
f := reflect.ValueOf(&u).Elem().Field(0)
fmt.Println(f.CanAddr(), f.CanSet(), f.CanInterface()) // true false false
fmt.Println(f.Int())                                 // 7
```

不能简单说“未导出字段完全读不到”。有些按 Kind 的读取方法可以读取它，但通过 `Interface()` 暴露或普通反射设置会受到限制。写通用映射器时应主动跳过未导出字段，不依赖 `unsafe` 绕过封装。

### `CanSet == false` 不代表底层内容完全不能改变

| 值 | 代表的位置可设置吗？ | 对底层数据的典型影响 |
|---|---:|---|
| `ValueOf(整数)` | 否 | 不能替换原整数 |
| `ValueOf(&整数).Elem()` | 是 | 可以修改原整数 |
| `ValueOf(slice)` | 否 | slice 元素通常可设置；替换调用方的 slice 变量需地址 |
| `ValueOf(array).Index(0)` | 否 | 按值拿到的数组元素不能设置 |
| `ValueOf(&array).Elem().Index(0)` | 是 | 可以修改原数组元素 |
| `ValueOf(map)` | 否 | 非 nil map 仍能通过 `SetMapIndex` 更新条目 |
| `MapIndex` 返回的元素 | 否 | 不能直接 Set；修改副本后需写回 map |

理解这里比记住“反射修改必须传指针”更准确：替换变量与修改共享底层数据是两个不同操作。普通 Go 对 slice、map 的语义也相同。

## 6. 结构体遍历与标签

```go
type User struct {
    ID       int64  `json:"id" db:"user_id"`
    Nickname string `json:"nickname,omitempty"`
    Password string `json:"-"`
    secret   string
}

t := reflect.TypeOf(User{})
for i := 0; i < t.NumField(); i++ {
    f := t.Field(i)
    if !f.IsExported() {
        continue
    }
    tag, present := f.Tag.Lookup("json")
    fmt.Println(f.Name, f.Type, tag, present)
}
```

这里遍历的是类型信息。若要读取某个用户的实际字段值，需要另一个 `reflect.Value`，使用 `v.Field(i)`。

标签本身是元数据。`json`、`db`、`validate` 等名字不会自动触发 Go 语言行为，是读取标签的库赋予它们意义。`Get` 和 `Lookup` 也不同：当标签值为空字符串时，只有 `Lookup` 的布尔结果可以区分“写了空值”和“没有这个标签”。

嵌入字段需要单独设计：

- `NumField` 枚举直接声明的字段，嵌入字段本身占一个位置。
- `FieldByName` 可能查到提升字段，也可能遇到同层重名歧义。
- `StructField.Index` 是访问路径，可用 `FieldByIndex`。
- 经 nil 嵌入指针访问内部字段可能失败；要么显式分配，要么返回带路径的错误。

本套实现题都限定为直接字段，不自动展开嵌套结构，避免把嵌入字段冲突的规则藏在实现里。

## 7. 赋值、转换与数值溢出

这三个检查不能互相代替：

1. `source.Type().AssignableTo(target)`：可以像普通赋值一样放进去吗？
2. `source.CanConvert(target)`：当前值能合法转换且不会因转换前置条件而 panic 吗？
3. 转换或写入后，数据是否满足业务要求、有没有数值截断？

```go
source := reflect.ValueOf(int64(257))
target := reflect.TypeOf(int8(0))

fmt.Println(source.Type().AssignableTo(target)) // false
fmt.Println(source.CanConvert(target))         // true
fmt.Println(source.Convert(target).Int())      // 1，转换合法但发生截断

dst := reflect.New(target).Elem()
fmt.Println(dst.OverflowInt(257))               // true
```

`SetInt` 接收 int64，并不意味着所有输入都能无损装进 int8。生产代码若要求无损，应先做溢出检查，或者用目标位宽调用 `strconv.ParseInt`。E06 与 E09 分别练习这两种做法。

`Type.ConvertibleTo` 是类型层面的判断；有些转换还依赖具体值，例如 slice 转固定长度数组依赖长度。因此需要检查当前值时使用 `CanConvert`，并另行定义是否接受截断、精度损失等情况。相关边界可查 [reflect Value 实现与说明](https://go.dev/src/reflect/value.go)。

本套 `SetField`、`Invoke`、`ScanRow` 一律选择严格赋值协议：`int64` 不自动变成 `int`，`"42"` 不自动变成整数。如果需要转换，先明确允许哪些转换、失败如何报告，再增加一层显式转换逻辑。

## 8. 动态创建、集合操作与函数调用

### 创建值与创建容器

| 需求 | API | 注意点 |
|---|---|---|
| 创建类型 T 的可写对象 | `reflect.New(t).Elem()` | `New` 自身返回 `*T` |
| 获得类型 T 的零值 | `reflect.Zero(t)` | 值有效，但本身不可设置 |
| 创建 slice | `reflect.MakeSlice(t, len, cap)` | t 必须是 Slice 类型 |
| 创建 map | `reflect.MakeMap(t)` | t 必须是 Map 类型 |
| 给 slice 追加 | `reflect.Append(v, item)` | 返回新的 slice Value，需要保存或写回 |
| 遍历 map | `MapRange()` | 不依赖 map 顺序 |
| 删除 map 键 | `SetMapIndex(key, reflect.Value{})` | 这里无效 Value 表示删除 |

删除 map 键与设置零值不同：`SetMapIndex(k, reflect.Zero(elemType))` 是保留键并写入类型零值。

### 动态调用函数

```go
add := func(a, b int) int { return a + b }
fn := reflect.ValueOf(add)
out := fn.Call([]reflect.Value{reflect.ValueOf(2), reflect.ValueOf(3)})
fmt.Println(out[0].Int()) // 5
```

`Call` 不替你验证业务协议。实际组件应先确认函数有效、非 nil、参数数量正确、每个参数可赋值，再调用。函数返回的 `error` 是业务结果；参数不匹配是调用器错误，两者应当分开。

变参函数要区分：`Call` 传入展开后的逐个参数，`CallSlice` 把最后一个 slice 作为 `...` 参数。例如 `f(1, 2, 3)` 与 `f(1, []int{2,3}...)`，对应的参数列表形状不同。原理示例中有可运行的对照。

### 方法集与接收者

```go
type Counter struct{ N int }
func (c *Counter) Add(n int) { c.N += n }

c := Counter{}
reflect.ValueOf(c).MethodByName("Add").IsValid()  // false
reflect.ValueOf(&c).MethodByName("Add").IsValid() // true
```

上面的类型与方法声明应放在包级。普通语法里可寻址变量的 `c.Add(1)` 可以自动取地址，但反射查找依据当前类型的方法集，不自动替你查到 `*Counter` 上的方法。

从 Value 获得的方法值已绑定接收者，`Call` 时不要再传接收者；从 `Type.Method` 得到的 `Method.Func` 则不同。方法集规则见 [Go 规范](https://go.dev/ref/spec#Method_sets)。

## 9. 工作场景：用什么、为什么用、边界在哪里

| 场景 | 运行时不知道什么 | 常用操作 | 首要边界 |
|---|---|---|---|
| JSON / 其他编码与解码 | 类型结构和字段协议 | Kind、字段、标签、Set | 不能把自制映射器当完整编码器 |
| 配置 / 环境变量加载 | 配置字段及其类型 | Tag、字符串解析、Set | 缺失与显式零值要分开 |
| 表单 / 请求绑定 | 请求字段对应哪个 Go 字段 | 字段索引、转换、Set | 限定可写字段，明确错误路径 |
| 参数校验 | 每个字段对应哪些规则 | Tag、Kind、IsZero | 业务“必填”不能只靠统一零值判断 |
| ORM / 数据行映射 | 列名对应哪个字段 | 字段映射、Set、接口扩展 | NULL、Scanner、数值与时间类型 |
| 日志 / 脱敏 / 审计 | 对象有哪些可记录字段 | 字段遍历、递归、标签 | 递归深度、循环引用、敏感字段策略 |
| 通用复制 / diff / 比较 | 嵌套的数据形状 | Kind 分派、递归 | 浅拷贝、引用共享、业务相等 |
| RPC / 动态处理器注册 | 函数签名与方法集合 | NumIn、In、Out、Call | 注册阶段校验，调用阶段保留错误边界 |
| 测试辅助 | 被测值结构 | DeepEqual、元数据打印 | 相等规则要符合业务 |
| 依赖注入容器 | 构造器输入输出类型 | Type、Implements、Call | 同类型多实例、循环依赖、生命周期 |
| 管理后台 / schema 工具 | 字段信息与展示提示 | StructField、Tag | 展示协议与业务模型解耦 |
| 动态 channel 集合 | 运行时需要等待哪些通道 | reflect.Select | 关闭的 channel 和退出条件 |

下面把几个常用场景串起来。

### 9.1 序列化与 map 转换

编码器知道“这是 string”才知道按字符串编码；看到 struct 才遍历字段；看到自定义编码接口又可以把控制权交还给类型本身。

```go
type AuditUser struct {
    ID       int64  `map:"user_id"`
    Name     string `map:"name"`
    Password string `map:"-"`
}

data, err := practice.ToMap(AuditUser{ID: 7, Name: "小明", Password: "secret"})
// 成功时仅包含 user_id 和 name。
_ = data
_ = err
```

这是 E05 的调用方式，需要导入本模块的 `practice` 包。它只做浅层映射，不复制内部 slice / map，也不实现 JSON 的嵌入字段、转义或循环引用规则。这里故意使用 `map` 标签：其 `omitempty` 用 `IsZero`，不会冒充标准 JSON 的完整语义。标准库的 `json` 标签和 `omitempty` 规则见 [encoding/json 文档](https://pkg.go.dev/encoding/json@go1.22.0#Marshal)。

读取标准库时，可观察类型分析如何与编码执行分离、为何需要字段缓存，见 [encoding/json 源码](https://go.dev/src/encoding/json/encode.go)。实际写业务优先用成熟编码器。

### 9.2 配置默认值 + 校验

```go
type Config struct {
    Host string `default:"localhost" validate:"required"`
    Port int16  `default:"8080" validate:"min=1"`
}

cfg := Config{}
if err := practice.ApplyDefaults(&cfg); err != nil {
    return err
}
violations, err := practice.Validate(cfg)
```

默认值组件读取字符串标签，根据目标 Kind 解析，再写入目标字段。校验组件使用同一组元数据，但执行读取与规则判断。两者职责不同，通常不该把“校验”顺手写成“修改”。

生产环境要额外回答：用户显式设置 `false` 或 `0` 时还要覆盖吗？如果不该覆盖，就使用 `*bool`、`*int`、可选值包装或单独记录来源，而不是仅依赖 `IsZero`。E06 为了聚焦反射，明确采用“零值表示待填充”的协议。

E06 还要求先完成全部解析再写入，防止前几个字段已改、后面字段解析失败，留下半更新配置。它提供的是失败时不写入，不提供多 goroutine 同时修改对象的并发事务。

### 9.3 模拟 ORM 行映射

```go
type UserRow struct {
    ID   int64  `db:"user_id"`
    Name string `db:"name"`
}

var user UserRow
err := practice.ScanRow(&user,
    []string{"name", "user_id"},
    []any{"小明", int64(7)},
)
```

E11 先根据 db 标签建立“列名 → 字段下标”的映射，再检查输入值是否可赋值，全部通过后写入。列顺序不需要与结构体字段顺序相同。

真实 `database/sql` 的 `Rows.Scan` 按位置写入目的值；自动按列名匹配结构体是更上层映射器的工作。标准库转换路径也不只是反射：它有常见类型路径，并支持 `sql.Scanner` 等扩展点，见 [Scan 转换源码](https://go.dev/src/database/sql/convert.go)。因此，不要把教学版 `ScanRow` 理解成 `Rows.Scan` 的完整复刻。

业务中还要定义 NULL 到指针、`sql.NullString` 等类型的映射，以及整数位宽、`[]byte` 生命周期、时间和自定义类型如何处理。

### 9.4 请求绑定与批量赋值

如果前端传来 `map[string]any`，不要直接遍历所有 key 并对同名字段 Set。先建立允许写入的字段表，再转换、校验并写入。例如更新用户资料只允许 Name、Avatar 等字段，不应因为结构体里有 Role 就自动允许修改它。

E04 练单个字段的严格赋值；E11 练批量准备后统一写入。它们的异常输入都应该返回可诊断错误，而非把字段名错误变成 panic。

### 9.5 动态注册、RPC 与依赖注入

框架可以接收任意函数，在启动时检查参数、返回值和上下文位置，把已经验证的函数放入注册表，运行时再反射调用。E08 先只实现固定参数的版本。

只有几种明确操作时，`map[string]func(...)` 或接口注册表往往已经够用。反射更适合允许注册不同签名、又必须在运行时检查签名的组件。

`net/rpc` 是理解按方法注册与调用的标准库例子；其包已冻结，不接受新特性，阅读目的主要是学习设计，见 [net/rpc 文档](https://pkg.go.dev/net/rpc)。这里的运行时动态性不意味着能凭字符串自动找到并载入任意 Go 包。

### 9.6 日志、脱敏与递归遍历

字段遍历可以生成审计信息，但应先设计记录协议：默认允许哪些字段？嵌套对象如何处理？指针循环如何终止？map 键和 slice 元素是否也遍历？输出是否稳定排序？

浅层 `ToMap` 中 `Password` 使用跳过标签，只是在调用者正确声明标签时生效；它不是完整的脱敏保障。P01 会要求你设计更明确的输出策略、深度限制和循环引用处理。

### 9.7 测试比较与业务相等

```go
fmt.Println(reflect.DeepEqual([]int(nil), []int{})) // false
fmt.Println(reflect.DeepEqual(int(1), int64(1)))    // false
fn := func() {}
fmt.Println(reflect.DeepEqual(fn, fn))             // false
```

`DeepEqual` 有明确的结构比较规则，不能替你决定“空集合与未提供集合是否相同”或“浮点数误差是否可接受”。对时间常应使用 `Time.Equal`，对业务对象可以先规范化再比较。

不要用两个 `reflect.Value` 直接 `==` 来判断被包装数据的业务相等；那是在比较 Value 包装本身。对于可比较值，可以理解 `Value.Equal` 与 `Comparable`，但 slice / map 等仍需要你选定比较协议。

## 10. 性能：测量成本，而不是背倍数

反射常见成本来自动态 Kind 分派、按名字查找、类型检查、值包装、动态调用，以及有些路径产生的分配。不同操作、数据形状、Go 版本和 CPU 下差异很大，不能笼统声称“反射固定慢十倍”。

常用优化路径：

1. 在注册或初始化阶段分析类型，保存字段下标、访问路径和规则。
2. 热路径尽量按缓存的下标访问，减少重复解析标签与按名查找。
3. 缓存 `reflect.Type` 对应的不可变元数据，不缓存某次请求的可变 `reflect.Value`。
4. 用接口保留特定类型的快速路径；必要时考虑生成代码。
5. 使用 benchmark 和实际 profile 决定优化是否有价值。

E10 使用 `sync.Map` 存元数据，并在返回切片时复制，防止调用者改坏缓存。缓存锁只保护缓存自身，不自动保护业务对象。动态类型数量很多时还要考虑缓存是否持续增长。

E12 会对比直接读取、按名字反射读取、按下标反射读取，以及带防御性复制的元数据缓存。测试一次字段读取不代表完整请求收益；缓存版本仍可能分配，复制也是 API 隔离带来的成本。

需要检查并发问题时使用 `go test -race`；它检测本次执行覆盖到的竞争，不代表证明了所有可能路径都安全，见 [Go race detector 介绍](https://go.dev/blog/race-detector)。

## 11. 接口、泛型、反射、代码生成怎么选

| 工具 | 主要依据 | 适合的例子 |
|---|---|---|
| 直接代码 | 已知具体类型和具体业务 | 修改 `user.Name`、订单状态流转 |
| 接口 | 共同的行为 | Store、Reader、Validator |
| 类型断言 / type switch | 有限且已知的动态类型 | 处理 string / []byte 两种输入 |
| 泛型 | 多种类型遵守同样的算法与约束 | 集合、数值算法、通用容器 |
| 反射 | 运行时发现结构，并依结构执行不同逻辑 | 通用编码、字段绑定、schema 提取 |
| 代码生成 | 类型集合构建时已知，运行时希望走静态路径 | 生成编码器、数据库映射代码 |

泛型并没有自动提供“枚举 T 的字段及标签”的能力，所以它不能直接取代基于结构分析的反射。它也能与反射组合，例如泛型入口负责返回具体的 T，内部仍反射分析字段。官方的选择讨论见 [When To Use Generics](https://go.dev/blog/when-generics)。

我的实践建议：先把协议写清楚，再选择能最直接表达协议的工具。不要为了使用某个语言特性，制造本来不存在的动态性。

## 12. 写反射组件时的工作顺序

拿到任意输入后，按下面的顺序思考：

```text
输入是否存在？
    ↓ IsValid
它属于允许的 Kind 吗？
    ↓ 判断指针 / 接口 / struct / map 等
是否需要解引用，是否为 nil？
    ↓ IsNil / Elem
字段、方法、键是否存在？
    ↓ 查找结果 IsValid 或存在标记
是否允许读取 / 写入 / 暴露？
    ↓ CanSet / CanInterface / 导出检查
输入类型、数值范围、业务规则是否满足？
    ↓ AssignableTo / 明确的转换与溢出检查
执行操作，返回有字段路径的错误
```

这不是让每个函数机械调用所有检查，而是根据你承诺的输入协议，证明下一步不会因为调用条件不成立而 panic。

项目里还应提前决定：是否处理多层指针、是否分配 nil 指针、嵌入字段重名如何处理、是否递归、循环引用如何终止、转换失败是否留下部分更新、共享状态由谁同步。
