# 05 · 答案与推理

建议先完成题目。完整编程题参考实现在 `lab/solutions.go`；可用同一套测试对照行为。

## A · 推理题答案

### Q01

不能打印。无缓冲发送等待接收，而接收在同一 goroutine 的后续语句中，无法到达。

可以把发送放进另一个 goroutine，形成一次会合；也可以改成容量 1，此时发送先入队而不必已有接收者。它们都能完成这个例子，但不能在所有同步推理中互换。

### Q02

第二次发送 `ch <- 2` 阻塞。容量改成 2 后两次发送可以完成，之后能收到 1。接收不需要先 close；close 用来表达未来不再发送，不是让接收生效的开关。

### Q03

```text
0 true
8 true
0 false
0 false
```

第三次第一次观察到关闭且排空。之后每次接收都立即返回零值和 false。首次收到的 0 是实际数据，不能只判断数值。

### Q04

打印 9 后等待下一项，不会打印 finished。唯一生产者确定不再发送时应 close。消费者随意 close 可能使仍在发送的生产者 panic；如果消费者希望停止，应通知取消并遵守关闭责任协议。

### Q05

原代码打印 default。nil 接收不能就绪；已关闭且排空的 channel 接收立即就绪，打印 0。对原来的 nil channel 调用 close 会 panic。

### Q06

依次打印 5、false。复制的是 channel 值，a、b 引用同一个队列与关闭状态。

### Q07

g 中 `close(in)` 不能编译。f 的发送和 close 都允许。发送能否完成还取决于是否有接收者或缓冲，类型正确不代表不会阻塞。

### Q08

一个发送值只交给一个接收者。初始化完成可用唯一初始化者 close(ready)，十个等待者分别 `<-ready`。这是一次性信号广播；若初始化可能失败，还需要发布结果或错误，避免把“结束”误解成“成功”。

### Q09

A、B 都可能。多个就绪分支按语言规则选择，源代码顺序不表示优先级。取消与数据同时就绪也可能选数据。

### Q10

空且未关闭时不断执行 default，产生空转。关闭后一直读到零值，可能反复处理无意义任务。

```go
for {
    select {
    case <-ctx.Done():
        return
    case job, ok := <-jobs:
        if !ok {
            return
        }
        process(job)
    }
}
```

process 若可能很慢，也要支持取消或有时间上界。

### Q11

普通 break 只退出最内层 select，外面的 for 仍继续。done 关闭后还可能形成高频循环。可以用 return 退出函数，或给 for 命名并 `break loop`。

```go
loop:
for {
    select {
    case <-done:
        break loop
    case n, ok := <-input:
        if !ok {
            break loop
        }
        use(n)
    }
}
```

### Q12

a 关闭且排空后持续返回零值；会消耗 CPU 并干扰 b 的处理。接收用 `v, ok`，!ok 时 `a=nil`。外层用 `for a!=nil || b!=nil`，或记录剩余输入数量；两者都结束才退出。若可能永不关闭，加取消分支。

### Q13

不能保证：两个生产者都可能观察到同一个空位，其中一个填满后，另一个仍会阻塞。len 本身可并发调用，不等于出现数据竞争；错误在于把瞬时观察当成之后操作的保证。

用 `select { case jobs <- job: ...; default: ... }` 表达立即尝试。前提仍然是发送期间不会发生关闭。

### Q14

关闭状态检查与发送不是一个不可分割操作。检查后 channel 仍可能被关闭。Once 只限制 close 执行次数，不能协调其他 goroutine 的发送。正确解法是先让所有潜在发送者停止并等待它们退出，再由唯一协调者关闭。

### Q15

存在数据竞争：传递 slice 不会复制底层数组。发送后修改 data[0] 与消费者读取同一个元素之间缺少同步顺序；最后等待 goroutine 结束不能修复已经发生的读写冲突。

可以发送 `append([]int(nil), data...)`，之后各自只操作自己的数组；也可以约定发送完成后把原数组的读写所有权交给消费者，发送者不再修改，直到收到归还确认。共享修改场景则需其他同步。

### Q16

保证打印 17。写入发生在 close 前，接收观察到关闭后才读取。Sleep 不建立这种同步关系，即使实际运行中常常“已经执行完”，也不能据此证明没有数据竞争。

### Q17

不保证。无缓冲发送只等到接收交接，不等 slowSave。让 worker 在保存后发送结果或 close(done)，调用者等待确认再打印；保存可能失败时，应返回 error，不能用无载荷信号把失败也宣称为 saved。

### Q18

容量 1 时有数据竞争：主 goroutine 可以把值放进缓冲后立即读 x，子 goroutine 可能还没写。

容量 0 时，子 goroutine 的 `x=7` 在接收前；无缓冲接收的同步关系保证对应发送完成后能观察到这个写入。因此打印 7。差异来自同步保证，不来自谁更快。

### Q19

某个 worker 先结束并关闭 out，其他 worker 再发送会 panic；其他 worker 之后重复 close 也会 panic。用 WaitGroup 跟踪所有发送者，由独立协调者 Wait 后 close。所有发送必须发生在各自 Done 之前。

### Q20

主 goroutine 等 Wait；worker 等 out 的接收者；接收循环又排在 Wait 后，形成循环等待。

让协调 goroutine 等待并关闭 out，主 goroutine立即接收：

```go
go func() {
    wg.Wait()
    close(out)
}()
for n := range out {
    fmt.Println(n)
}
```

这不依赖提前知道结果数量，也不需要猜缓冲容量。

### Q21

slowCompute 返回后，子 goroutine 卡在无缓冲发送，因为原接收者已退出。一次发送可以用容量 1 接住结果，或者使用能响应取消的发送。

缓冲不能中断 slowCompute，也不能推广成“无限结果流随便加一个缓冲就不会泄漏”。实际耗时操作应支持 ctx；不支持时必须承认调用方只能停止等待，不能确保任务已经停止。

### Q22

不会因启动满一秒就自动结束。每轮重新创建计时器，持续事件会不断重启等待窗口，表达的是空闲时间。

总超时应把 timer 放在循环外，或循环外创建 WithTimeout，并在循环中监听同一个 Done。两个条件同时就绪时仍要接受 select 的选择语义；若每轮工作很慢，总退出时间还取决于工作能否中断。

### Q23

```text
computed
canceled
```

即使 out 是 nil，发送右侧仍会在进入选择时求值。context 无法跳过卡在表达式求值里的阻塞调用。先检查 ctx 只能减少已取消情况下的无用工作，不能强制打断后续函数。

### Q24

组织整条流水线的上层负责取消所有参与阶段。每层的输入接收、输出发送以及实际 I/O 都要有可取消或有界结束的路径。Take 不能知道其他输入消费者是否仍需工作，也不能证明其他发送者已经停下，所以不应关闭输入。

取消之后若需要确认资源清理完成，还要等待各阶段退出；仅调用 cancel 并不等于已完成清理。

## B · 参考实现应怎样审查

不要只检查“测试通过”，还要逐个说明不变量。

| 题目 | 最重要的不变量与边界 |
|---|---|
| E01 | 不 close 输入；循环只在输入关闭且排空后结束 |
| E02 | 没有阻塞路径；没有 goroutine；关闭安全由调用协议提供 |
| E03 | 提前取消先返回；输入关闭与取消用不同返回值表达 |
| E04 | 唯一发送者唯一关闭；复制输入；每次发送可取消 |
| E05 | 读取和交付均可取消；fn 的执行时间由 fn 契约决定 |
| E06 | 每个输入只有一个转发者；所有 Done 后才关闭 out |
| E07 | 不超额读取；n<=0 不碰输入；上层负责取消上游 |
| E08 | 固定 worker；回调并发<=workers；每个正常任务回报一次 |
| E09 | 每个任务一次回报；buffer 足以容纳所有回报；不等待失败方清理 |
| E10 | batch 长度<=size；发出后不改写数组；取消不强行发尾批 |

### 为什么关闭位置是安全的

E04、E05、E07、E10：各自只有一个 goroutine 发送到自己的 out，defer close 在最后一次发送之后执行。

E06、E08：每个发送者在退出前调用 Done；协调者 Wait 之后才 close。因此只要回调遵守契约，关闭时已无发送者。

E09：不 close 结果 channel，因为没有消费者依赖 range 结束，也不需要一个额外协调者。它有固定回报上界，消费方按数量或首次成功结束。所有任务最终返回后，相关对象失去引用即可被回收。

### 为什么所有阻塞点都需要审查

不要只搜 `case <-ctx.Done()` 就判定“支持取消”。应找出每一处可能等待的位置：输入接收、输出发送、信号量获取、回调、Wait，以及外部 I/O。其中每一处都要有退出理由。

这些练习中，E01 故意等待有限输入关闭；E02 根本不等待；其余收发用 context；E08 的回调和 E09 的任务必须配合取消。Wait 的可终止性依赖被等待者能退出。

### 为什么取消没有严格优先级

参考实现在若干循环入口检查 ctx.Err，减少取消后的额外工作。但如果取消发生在检查之后，数据分支与取消分支可能同时就绪，仍允许选中数据。不能把这些例子当作“cancel 返回后绝不再启动业务操作”的实现。

### 测试保证到什么程度

测试覆盖正常完成、关闭与零值、空输入、nil 输入、取消、非法参数、单项错误、并发上限、首个成功、tick 刷新、切片别名等行为。

通过测试与 race detector 只说明已执行路径未暴露相应问题。它们不自动证明所有调度下都无泄漏，也不证明调用方回调遵守契约。尤其是取消后的收集动作可能使某些错误的阻塞发送暂时得以继续，仍需按上面的阻塞点审查实现。

## C · 综合项目的设计方向

### P1：入口状态、在途提交者、排空阶段

一种可行设计：用 Mutex 保护 accepting 状态，以及“已经登记、但发送流程尚未退出”的提交者计数；登记和关闭入口必须在同一个状态协议内进行。

Submit 在锁内确认 accepting 并登记，然后释放锁，在 select 中尝试 jobs 发送、调用方取消或服务关闭入口通知；任何路径退出都注销。不能持有状态锁阻塞发送。

Shutdown 在锁内改为不再接受新登记，并触发停止接单信号，然后在锁外等待已登记的提交者退出。此后才能 close(jobs)。如果用 WaitGroup 计数，必须保证关闭登记入口之后不会再发生新的正数 Add，再启动相应 Wait；不能让“检查接受状态”与“登记”分离。

与停止信号并发的提交可能成功发送，也可能被拒绝，API 要明确：成功的都算已接收，必须排空；Shutdown 开始并被观察之后的新提交被拒绝。若要求更强的线性化规则，要让提交确认与关闭状态共享一个原子的协调协议。

worker 从 jobs 读到关闭才结束，并继续发送结果；独立收集者一直消费。协调者等 worker 全部退出后 close(results)，再等收集者结束。排空超时只结束等待，不能谎称已经完成清理；另有强制取消工作 context 的路径。

重复 Shutdown 可共享同一个完成 channel；由唯一协调流程实际 close。`sync.Once` 只适合保护“发起关闭流程一次”，不能替代提交协议。

### P2：顺序与内存是两个目标

先给每项加 Index，让 worker 无序计算，汇总后按 Index 还原。若流式交付，持有 nextExpected 与 pending map：收到乱序项先存储，连续项到齐后逐个交付。

慢的第 0 项会让后面的结果不断堆积。仅把结果 channel 设为小缓冲，不能限制 pending map。要限制窗口，必须限制已经提交但尚未按序交付的索引范围；交付推进后才能开放新任务。

### P3：完成确认必须抵达实际 writer

把“入口接收”和“写入成功”设计为不同的确认，错误级日志需要跟踪到 writer 结果。批量合并后，要能把每项的确认关联回原请求。

调试级日志过载时明确丢弃并记录计数；writer 失败时限制重试次数、退避时间与缓存总量。测试用手动时钟和 gate，验证关闭时尾批确实到达 writer 并得到结果，而不是只进入另一个 channel。

所有进程内确认都不能直接推出“进程崩溃仍不丢”。若要求这一点，需要定义并验证持久化边界。
