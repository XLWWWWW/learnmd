# 04 · 分层提示

先只看提示 1。尝试至少十分钟后，再看提示 2。完整代码在 `lab/solutions.go`，建议最后对照。

## E01

**提示 1：** 对 channel 使用 range 的结束条件是什么？

**提示 2：** 初始化 total=0，在 range 中累加；循环退出后返回。不负责关闭输入。

## E02

**提示 1：** 什么结构可以表达“通信不能立刻完成就走另一条路径”？

**提示 2：** 一个发送 case，加 default。不要先读取 len，也不要另开 goroutine。

## E03

**提示 1：** 你需要区分“读到零值”和“没有读到真实数据”。

**提示 2：** 先处理进入前已经取消的 ctx，然后 select 等待输入或 ctx.Done。输入用 `v, ok := <-in`。不要从函数内部 close(in)。

## E04

**提示 1：** 谁创建输出，谁控制发送，谁就能证明以后没有发送。

**提示 2：** 返回前复制 nums；启动一个 goroutine，defer close(out)。每次发送都 select 等待 out 或取消。循环前检查 ctx.Err 可以减少取消后的额外发送，但不能创造原子优先级。

## E05

**提示 1：** 有两个可能永久等待的位置，分别在哪？

**提示 2：** 一次 select 负责读取输入，检查 ok；计算 value；另一次 select 负责发送输出。唯一 goroutine defer close(out)。fn 本身能否中断取决于它的契约。

## E06

**提示 1：** 不要让任何单个转发者宣称“所有发送都结束”。

**提示 2：** 启动前 `wg.Add(len(inputs))`，每个转发者 defer Done，另一个协调 goroutine Wait 后 close(out)。转发者的收、发各有一个取消分支。零输入时 Wait 立即完成。

## E07

**提示 1：** 最多循环 n 次，不意味着输入一定有 n 项。

**提示 2：** 每轮可取消地接收，遇到 !ok 结束；再可取消地发送。n<=0 时根本不进入循环。把“通知上游停止”留给组织流水线的调用方。

## E08

**提示 1：** 启动 workers 个固定循环；它们可以直接从同一个 in 取任务。

**提示 2：** 每个循环读输入、执行 fn、发 Result。单项错误是 Result 的一部分。取消可以停止等待和交付，但 fn 需要自己使用 ctx。关闭模式沿用 E06，Wait 负责证明所有发送者退出。

**进一步提示：** 结果收集要与 worker 执行并发进行。不要在返回 out 之前先 Wait，也不要在接收前等全部 worker。

## E09

**提示 1：** 每个任务只回报一次，可以计算出所有回报的数量上界。

**提示 2：** 创建可取消子 context，创建容量 len(jobs) 的结果 channel，为每个 job 启动 goroutine。收集时遇到成功立即返回；失败累积；收够全部失败后 errors.Join。defer cancel 处理所有返回路径。

**进一步提示：** 只需要固定次数接收或提前返回，因此不必 close 结果 channel。容量只能解决任务返回后的发送阻塞，不能终止不响应 context 的任务。

## E10

**提示 1：** 把“刷新”提取成一个操作：空批次无事可做，非空批次可取消地发送。

**提示 2：** select 处理 input、ticks、ctx.Done 三类事件。输入关闭时刷新一次后 return；tick 关闭时设为 nil；每次发出切片后，下一批使用新底层数组。

**进一步提示：** 正常关闭要发尾批，取消不要求发尾批。这两条路径不要统一写成无条件 `defer flush()`，否则取消后可能重新堵在发送上。

## 综合题提示

P1：先把“允许提交”与“已经进入发送流程的提交者”分别建模。关闭入口后，等后者退出才能 close(jobs)。审查是否有 Wait 与状态锁相互等待。

P2：给任务加索引；先做全量汇总排序，再挑战流式有界重排。排序正确不代表内存有界。

P3：把时钟和 writer 都做成可控制的依赖；数据入口确认、批次交付确认、最终落地确认是三个不同阶段。
