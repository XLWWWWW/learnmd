# 06 · 在工作中审查和排查 channel 代码

## 提交代码前的十个问题

1. 每个 channel 传递什么：数据、结果、令牌，还是一次性信号？
2. 谁可以发送？谁是关闭者？关闭时如何证明不会再有发送？
3. 每条 `go` 语句启动的任务，正常完成和提前取消时各从哪里退出？
4. 每个可能阻塞的接收、发送、回调和 Wait，最终由谁推进？
5. 消费者只要第一项、遇错返回或请求取消时，上游会怎样？
6. 队列满时是等待、超时、拒绝还是丢弃？调用方能观察到什么？
7. 缓冲和 worker 限制了哪些资源？还有哪些地方可能无限积压？
8. 元素中的 slice、map、指针由谁修改？发送后是否仍共享可变数据？
9. 错误会继续、整体取消，还是等待其他成功？收到结果是否代表业务已落地？
10. 停止请求与清理完成是否分开？真正需要等待完成的调用点是否等到了？

## 看到症状，从哪里开始找

| 症状 | 优先检查 |
|---|---|
| `send on closed channel` | 接收方擅自关闭；多发送者尚未退出；入口提交与 Shutdown 竞态 |
| `close of closed channel` | 多个 worker 都关闭；多个调用方重复发起关闭 |
| `close of nil channel` | 零值字段未初始化；关闭责任混乱 |
| `all goroutines are asleep - deadlock` | 同 goroutine 无缓冲收发；Wait 排在接收前；循环等待 |
| 请求结束后 goroutine 数持续上涨 | 无人接收的结果发送；nil/未关闭输入；I/O 不支持取消 |
| CPU 高但没什么业务 | for-select-default 空转；关闭输入未检查 ok；break 只跳出 select |
| 输出大量零值 | 已关闭 channel 反复接收；未区分真实零值与结束 |
| 结果顺序变化 | 多 worker 或多发送者；将打印顺序误当通信保证 |
| 内存持续上涨 | 任务/结果无界；大量等待的 goroutine；元素间接持有大对象 |
| 取消之后还发生少量处理 | select 多分支就绪；缺少更强的入口和完成协议 |
| -race 报共享对象冲突 | 发送 slice/map/指针后继续改写；回调共同修改共享状态 |

## 最小排障过程

先画等待关系，而不是立刻增加缓冲：

```text
goroutine A 等待什么？
谁能使这个等待继续？
那个人现在又在等待什么？
是否形成循环？是否存在永远不会出现的发送者/接收者？
```

服务里部分 goroutine 卡住时，未必触发全局 deadlock。可以通过 goroutine profile / 栈查看它们停在 send、receive、Wait 还是外部调用。`chan send`/`chan receive` 只是定位线索，不能单凭某次栈就判定泄漏；正常背压也会等待。

在可复现的测试里：

```bash
go test ./... -timeout 30s
go test -race ./... -timeout 60s

# 只在怀疑调度相关问题时，重复特定测试。
go test -race ./lab -run '^TestE08' -count 20 -timeout 60s
```

测试超时通常会提供 goroutine 栈，先从被卡住的那一行逆向找协议缺口。Race detector 只能检测实际执行到的路径，不会替你判断业务上的丢失、重复或所有泄漏。[官方 race detector 说明](https://go.dev/doc/articles/race_detector)

## 测试怎样写得可靠

- 用一个 gate 控制“任务已开始但尚未完成”，用 started/finished 信号确认阶段，而不是 Sleep 后猜状态。
- 并发上限同时检查两边：确实能并发到 W，也绝不超过 W；只检查<=W 可能让串行实现蒙混过关。
- 对无序结果比较集合/计数；只有承诺顺序的 API 才比较序列。
- 用 errors.Is 验证错误身份；不要靠完整错误字符串。
- 用手动 tick 或注入时钟测试批量逻辑；不要假设机器一定在 10ms 内调度完。
- 超时是挂死保护，不能作为“这一刻任务一定发生”的证明。
- 正常结束、输入关闭、输入永不产生、下游提前退出、取消中途到达，都分别考虑。
- 代码审查仍须逐个检查阻塞点；收集测试输出本身可能解除错误的发送等待。

## 迁移到业务代码时补上的内容

这些练习突出并发协议。真实服务还要结合具体需求补上日志和指标、错误关联、请求幂等、I/O 截止时间、重试上限、连接池容量与持久化边界。

建议从一条有明确输入和输出的小业务流水线开始改写。为它写下容量、关闭责任和取消传播；再模拟慢下游与提前返回。能解释它为什么不会无限等待，才适合继续扩展。
