# 02 · 日常工作中的 16 类场景

以下相对路径命令默认在工程根目录执行。标注“片段”的命令需要换成你自己的路径/服务，工程不会自动操作真实系统。可以先建 `scratch/` 做实验：`mkdir -p scratch`。

## 1. 为项目提供统一命令入口

**场景：** 同事总要记住很长的构建、测试、启动命令，希望入口固定。

```bash
./practice.sh help
./practice.sh E01
./practice.sh demo logs
```

本工程的 `practice.sh` 就是一个完整例子：用 `case` 分发子命令，计算脚本所在目录，检查必要依赖，再使用 `exec` 将状态直接交给测试程序。使用者从任何目录调用，行为都一致。

工作中可以同样封装 `dev.sh test|build|lint`。保持 stdout 是结果、stderr 是日志，未知子命令返回非零。不要把用户输入拼进 `eval`，也不要在脚本中默默切换到另一版本的工具链。

对应：E01、E04、E08。

## 2. 按环境提供默认配置

**场景：** 本地默认配置直接可用，CI 和预发环境可覆盖。

```bash
./solutions/e02.sh
APP_ENV=staging APP_PORT=9090 ./solutions/e02.sh
./practice.sh demo config
```

E02 展示环境默认值；E09 读取明确的 `KEY=VALUE` 数据格式。决定空串是否等于“未配置”，再选 `${x:-default}` 或 `${x-default}`。端口、并发数、超时时间必须在使用前校验范围。

真实服务一般定义优先级，例如“命令行 > 环境变量 > 配置文件 > 内建默认”。E02/E09 没有替你实现整套配置合并；把这个规则作为 P03 的扩展。

配置中有密码时，避免打印完整环境、`bash -x`、把密码放进进程参数。不要对数据配置使用 `source`；E09 的测试特意包含字面量 `$(touch pwned)`，它必须只是字符串。

对应：E02、E03、E09。

## 3. 对接收的任务清单逐行处理

**场景：** 同事给你一份服务名、URL 或 ID 清单，需要保留空格、反斜杠和最后一行。

```bash
./solutions/e05.sh fixtures/lines.txt
```

基本模式是 `while IFS= read -r line || [ -n "$line" ]; do ...; done < file`。一行一个任务只是协议选择；如果任务本身允许换行，就需要 NUL、JSON Lines 中的转义或其他明确协议。

不要让循环体中的子命令意外读走清单的 stdin。比如逐行运行远程命令时，某些 SSH 调用需要 `ssh -n`；本地不需要输入的 worker 可以 `</dev/null`。改变为管道输入后，别忘了外层变量作用域也会变化。

对应：E05、Q11、Q12。

## 4. 快速分析日志与生成日报

**场景：** 从日志按服务统计请求数与 5xx 数，输出可用于告警或日报的结果。

```bash
./practice.sh demo logs
# service  requests  5xx（实际是 TAB 分隔）
# api      3         2
# worker   2         0
```

E06 使用 awk 聚合、sort 稳定排序；坏行导致整体失败，避免“看起来成功但漏掉部分日志”。现实中也可能选择跳过坏行并计数，但必须在报表和状态中明确体现，不能悄悄忽略。

日志格式在本工程固定为四列，不等于完整 Nginx/Apache 格式。结构化 JSON 日志应交给 jq 或 JSON 解析器。大文件适合流式过滤和聚合，不要先用 `content=$(cat huge.log)` 把整个日志装入变量。

对应：E06、E16、P01。

## 5. 按字面值查找、排序、去重

**场景：** 排查某个错误码、请求 ID 或含正则符号的字符串。

```bash
./solutions/e16.sh 'ERROR' fixtures/access.log
./solutions/e16.sh 'DOES_NOT_EXIST' fixtures/access.log
```

第二条成功返回空结果。grep 的 1 应按“没有匹配”处理；读取失败或排序失败仍必须返回非零。E16 通过立即保存 `PIPESTATUS` 区分每个阶段，避免靠管道末段成功掩盖前段错误。

用户输入作为字面值时用 `grep -F -e "$needle"`，不要无意中当成正则。若业务允许正则，文档就要明确，并把无效表达式当输入错误处理。

对应：E16、D05。

## 6. 批量发现文件、预览整理计划

**场景：** 找出所有日志或图片，再逐个校验、压缩或搬运。

```bash
./solutions/e07.sh fixtures > scratch/log-files.nul
while IFS= read -r -d '' file; do
    printf 'candidate: %q\n' "$file"
done < scratch/log-files.nul
```

第一条命令如果失败，不应继续依赖不完整的清单。写成正式脚本时用 `if` 或 `|| exit` 检查，再开始处理。展示用 `%q` 可让换行、空格等特殊字符可见；机器处理仍使用 NUL。

删除旧日志属于更高风险的具体操作，先做只读计划：限定根目录、文件类型、名称规则、时间基准、符号链接策略，再输出候选路径。确认契约和测试后才设计实际执行入口。`find -mtime +7` 涉及按 24 小时区间取整，不能简单理解成“最近第 7 个日历日”。

对应：E07、E08；P02 的保留策略扩展。

## 7. 带 dry-run 的命令包装

**场景：** 批量任务先展示实际会传递什么参数，再执行。

```bash
./solutions/e08.sh --dry-run -- printf '%s\n' 'a b' '*.log'
./solutions/e08.sh --run -- printf '%s\n' 'a b' '*.log'
```

dry-run 打印每个参数的 Bash 转义表示，不执行命令。实际运行传递同一组参数，保留空串、空格、星号；子命令失败就透传状态。

dry-run 只能展示命令和参数，不能证明外部命令没有副作用，也不是权限隔离。不要把预览输出再交给 eval。需要保存计划供机器执行，应定义结构化格式与校验规则。

对应：E08、D07。

## 8. 更新配置、报表或缓存

**场景：** 生成新文件时，不希望用户或服务读到一半内容。

```bash
printf 'version=1\n' | ./solutions/e10.sh scratch/settings.conf
cat scratch/settings.conf
```

E10 在目标同目录创建临时文件，完整读取 stdin 后再发布，失败保留旧内容。临时文件权限为 0600；生产中如果服务需要其他读权限，要先明确设置和校验权限，再发布。

如果上游是生成器，`generator | writer` 里的 writer 看见 EOF 并不能区分“上游正常结束”与“上游异常退出”。需要“只有完整生成成功才发布”时，先将上游输出写到临时产物并检查成功，再调用 writer；单凭 writer 内部的 `cat` 成功不够。这也是 P01 组合阶段必须考虑的边界。

对应：E10、D04。

## 9. 备份并验证恢复

**场景：** 备份小型项目配置、静态文件或离线数据目录。

```bash
./practice.sh demo backup
```

演示只创建临时样本，归档后解压到另一目录并逐字节比对，最后清理。E11 对已有目标拒绝覆盖，拒绝将归档放进源目录；先生成并检查归档，再通过同目录硬链接发布，防止两个任务无意覆盖同一个文件。

备份设计还要决定：命名冲突、权限、归档一致性、保留周期、空间不足、恢复目标、校验与告警。完整恢复并比对，比“tar 返回成功”更有价值。不要随意解压来源不可信的归档；这里的演示归档全部由本工程创建。

对应：E11、P02。

## 10. 网络检查和有限重试

**场景：** 检查服务是否可用，或在短暂网络波动后再尝试一次。

本地演示，不访问网络：

```bash
./solutions/e12.sh 3 0 -- bash -c 'printf "attempt\n" >&2; exit 7'
# 尝试 3 次，最后返回 7。
```

真实服务的片段（需要 curl；URL 替换成自己有权访问的服务）：

```bash
# ./solutions/e12.sh 3 1 -- curl --fail --silent --show-error \
#     --connect-timeout 3 --max-time 10 --url 'https://your-service.example/health'
```

网络超时和尝试次数分别约束单次与总工作量。E12 不自带超时和错误分类，每次子命令的 stdout 都会原样转发，因此失败尝试输出了半份内容时不会自动回滚。写入结果要和 E10/P01 的阶段设计一起考虑。

只重试可安全重复的操作。健康检查适合；创建订单等操作需要业务幂等保障，不能仅把命令套进循环。

对应：E12、Q22。

## 11. 临时工作目录与中断清理

**场景：** 下载、解包、转换等多步任务需要临时空间，成功或失败后都应回收。

```bash
./solutions/e13.sh -- bash -c 'printf "%s\n" "$WORK_DIR"; printf data > "$WORK_DIR/result"'
```

脚本通过环境变量提供独立目录，子命令退出后清理。测试不仅检查正常成功，还检查子命令失败和 TERM 中断；中断时先通知直接子进程并 wait，再清理。

本例用可信命令演示。E13 的契约不覆盖忽略 TERM 的程序、完整后代进程树和 SIGKILL；生产中由 supervisor、容器/系统任务管理机制处理这些生命周期更合适。

对应：E13、Q19、D06。

## 12. 防止定时任务重叠

**场景：** 任务每 5 分钟启动，但偶尔执行超过 5 分钟；重入会争抢文件。

```bash
./solutions/e14.sh scratch/report.lock -- printf 'run once\n'
```

mkdir 成功才执行；锁被占用返回 75，原持有者不受影响。失败后释放自己拥有的锁。这个锁表示“整个业务任务”的所有权，不能任务启动后立刻删除。

目录锁在强杀后可能残留；应明确人工核实与恢复流程，不要以固定时间盲目删除。多个机器共享目录时还要评估网络文件系统语义。

对应：E14、D08。

## 13. 有界批量任务

**场景：** 对一组本地文件运行转换器、检查器或独立任务，希望加速但不耗尽资源。

准备可执行 worker（可放 `scratch/worker.sh`）：

```bash
#!/usr/bin/env bash
printf 'item=<%s>\n' "$1"
```

然后：

```bash
chmod +x scratch/worker.sh
./solutions/e15.sh 2 "$PWD/scratch/worker.sh" -- 'one item' two three
```

最多两个任务同时执行。某项失败仍完成全部项，最终返回 1；输出顺序不保证。根据 CPU、网络限流和文件描述符预算选择上限，不要仅按“越多越快”决定。

E15 按批等待，容易证明并发上限；慢任务可能导致空闲槽位。需要动态补位时可以在支持的 Bash 上管理 `wait -n`，或使用更成熟的并发执行工具，但仍要保留任务归属和错误汇总。

对应：E15、P03。

## 14. cron、CI 与非交互环境

**场景：** 终端手动成功，定时任务或 CI 却失败。

排查：解释器是否一致；PATH 是否包含工具；工作目录是否正确；输入是否等待交互；权限和 locale 是否一致；stderr 在哪里；退出码是否上传给调度系统。

非交互任务入口片段：

```bash
#!/usr/bin/env bash
project_dir=$(CDPATH= cd -- "$(dirname -- "$0")/.." && pwd) || exit 1
cd "$project_dir" || exit 1
export LC_ALL=C
exec ./practice.sh solution
```

不要依赖 `.zshrc` 中的 alias；用绝对路径或明确 PATH。cron 表达式、时区、日志轮转属于部署配置，本工程不创建任何真实计划任务。集成 CI 时执行 `check` 和 `solution` 验证材料；如果验收自己的进度，应该执行 `all`。

对应：E02、E14、工作检查表。

## 15. 构建与发布步骤编排

**场景：** 构建 → 测试 → 生成产物 → 发布，需要保证失败时停止后续步骤。

先在函数内部明确返回失败，再在主流程中决定后续动作。不要假设 `set -e` 会穿透函数在 if 条件中的所有失败。将产物生成与发布拆开：产物完整且校验通过才更改对外可见的目标。

模拟片段，函数名需要自己实现：

```bash
build_artifact || exit 1
test_artifact || exit 1
publish_artifact || exit 1
```

回滚不是简单的“发生错误就执行上一步反命令”；要知道旧版本、数据库迁移、外部副作用是否可逆。Shell 适合编排现有的构建与发布工具，不适合凭几行命令假装实现完整事务。

对应：E10、E12、E14；D03。

## 16. 巡检与信息汇总

**场景：** 收集磁盘使用、进程状态、文件是否存在、依赖工具版本，供人工排查。

本工程可直接运行 `./practice.sh doctor` 查看依赖。巡检脚本应区分“检查通过”“检测到问题”“检查本身失败”，避免命令不存在时仍打印绿色结果。

例如 `df -P` 更适合获取较稳定的格式，但挂载路径可能有空格；不同系统的 `ps`、`stat` 输出也不完全一样。能使用系统的结构化接口时优先使用接口。需要多主机、持续采集、长期告警时，监控系统比循环执行 Shell 更合适。

把一条临时排查命令升级成团队工具时，补上参数文档、错误状态、可重复测试和一份失败示例，比增加彩色输出更有价值。
