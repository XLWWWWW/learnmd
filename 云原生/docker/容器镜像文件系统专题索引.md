# 容器镜像文件系统专题索引

这个专题把容器镜像从 registry 中的一组内容对象，一直串到容器最终看到的 rootfs，并进一步解释镜像导出、OverlayFS Copy-on-Write、历史层泄露、Squash 和多阶段构建。

如果只记住一条主线，可以记成：

```text
镜像引用 tag / digest
  -> Image Index / Manifest
  -> Image Config + filesystem layers
  -> 解压并按顺序应用 layers
  -> OverlayFS lowerdir + upperdir
  -> merged rootfs
  -> 容器运行时挂载和进程
  -> export、分析或 squash
```

## 2. 整体心智模型

### 2.1 镜像存储阶段

```text
image:tag
   |
   v
Image Index（多平台时）
   |
   v
Image Manifest（单平台）
   |
   +-- Image Config
   |     +-- Entrypoint、Cmd、Env、User、WorkingDir
   |     +-- rootfs.diff_ids
   |
   +-- Layer Blob 0
   +-- Layer Blob 1
   +-- Layer Blob 2
```

这一阶段关注的是镜像如何寻址、校验、分发和保存。重点阅读前两篇笔记。

### 2.2 rootfs 准备阶段

```text
OCI manifest 顺序：
base layer -> middle layer -> top layer

OverlayFS lowerdir 顺序：
top layer : middle layer : base layer
```

容器运行时解压 layers、处理 whiteout，并使用 snapshotter 或 graph driver 创建统一文件系统：

```text
lowerdir：镜像只读层
upperdir：容器可写层
workdir：OverlayFS 内部工作区
merged：容器看到的 rootfs 视图
```

这一阶段重点阅读 OverlayFS 笔记。

### 2.3 容器启动阶段

只有 rootfs 还不等于完整容器。运行时还需要：

```text
rootfs
  + /proc、/sys、/dev 等挂载
  + /etc/hosts、hostname、resolv.conf 等运行时内容
  + namespaces、cgroups、capabilities、seccomp
  + 环境变量、用户、工作目录
  + Entrypoint 和 Cmd
```

Dockerfile 中的 `RUN` 在构建镜像时已经执行并写入 layers；`ENTRYPOINT` 和 `CMD` 只有启动容器时才执行。

### 2.4 分析与修复阶段

```text
研究原始镜像结构  -> docker save / OCI layout
查看最终镜像 rootfs -> crane export / BuildKit --output
查看容器当前状态  -> docker export
动态联合挂载      -> OverlayFS / containerd snapshotter
清除历史层内容    -> 重新构建，必要时 squash
```

## 3. 按问题查阅

### 镜像为什么不是一个 tar 包

阅读 [容器镜像内部结构详解](./容器镜像内部结构详解.md)。重点关注 descriptor、manifest、config、layer、DiffID、ChainID 和多平台 index。

### 怎样找到 OCI layout 中的 layer blob

阅读 [OCI Image Layout 与容器镜像结构](./OCI_Image_Layout与镜像结构.md)。重点关注 `index.json`、`blobs/sha256/`、media type 和 digest 跟随过程。

### 多个 layer 为什么能看到一棵普通目录树

阅读 [使用 OverlayFS 联合挂载容器镜像层](./使用OverlayFS联合挂载容器镜像层.md)。重点关注 `lowerdir` 顺序、文件遮挡、copy-up、upperdir 和 merged 视图。

### `docker save` 与 `docker export` 有什么区别

阅读 [提取容器镜像的根文件系统](./提取容器镜像根文件系统.md)。简单来说：

```text
docker save   保存镜像的分层对象和元数据
docker export 保存某个容器的文件系统视图，不包含 volume 内容
crane export  从镜像 layers 重建静态 rootfs
```

### 为什么 `rm` 后镜像大小没有下降

阅读 [容器镜像 Squash、体积治理与泄露凭据清理](./容器镜像Squash与泄露凭据清理.md)。新 layer 中的删除只会遮住下层文件，不能修改已经发布的旧 blob。

### 为什么删除的 token 仍可能被恢复

同样阅读 Squash 笔记。最终 rootfs 中看不到秘密，不代表历史 layer、image config、构建日志、缓存和 provenance 中不存在秘密。

### 怎样从源头构建更小、更安全的镜像

阅读 [Docker 多阶段构建实践笔记](./Docker多阶段构建实践笔记.md)。核心方法包括 builder/runtime 分离、BuildKit secret mount、`.dockerignore`、同层清理和依赖缓存控制。

## 4. 最容易混淆的概念

| 概念 | 保存什么 | 是否包含运行时变化 |
| :--- | :--- | :---: |
| Image layer | 一次构建产生的文件系统变化集 | 否 |
| Image config | 默认启动参数、平台、DiffIDs 等 | 否 |
| OCI layout | manifest、config 和 layer blobs 的本地内容寻址布局 | 否 |
| Image rootfs | 所有镜像 layers 应用后的最终静态文件系统 | 否 |
| Container writable layer | 某个容器创建后的新增、修改和删除 | 是 |
| Container rootfs | 镜像 rootfs 加容器可写层形成的视图 | 部分包含 |
| Running container filesystem | rootfs 加 volumes、bind mounts、proc、sysfs 等 | 是 |
| Squashed image | 将最终可见 image rootfs 重新打成一个 layer | 不应包含容器运行变化 |

### 4.1 “删除”的三个不同含义

```text
在 merged 中 rm 文件
  -> upperdir 创建 whiteout，下层文件仍存在

在后续 Dockerfile RUN 中 rm 文件
  -> 新镜像 layer 记录 whiteout，旧 layer blob 仍存在

重新构建或 squash 后不再引用旧 layer
  -> 新镜像不包含旧文件，但旧镜像和缓存副本仍可能存在
```

### 4.2 “扁平文件系统”的两个不同含义

```text
OverlayFS merged：动态统一视图，没有复制出完整第四份目录
Squashed layer：把最终可见 rootfs 重新归档成一个真实的新 layer
```

## 5. 实验学习路线

可以按照下面的顺序动手：

1. 使用 `crane pull --format oci` 保存一个单平台镜像。
2. 从 `index.json` 找到 manifest，再读取 `.layers[].digest`。
3. 将每个 layer blob 分别解压，观察新增、覆盖和 whiteout。
4. 使用 OverlayFS 按“顶层到基础层”的顺序联合挂载。
5. 在 merged 中创建和修改文件，观察 upperdir 的 copy-up。
6. 对比 `crane export`、`docker create + docker export` 的结果。
7. 使用 `docker history` 和 `dive` 查找体积浪费及历史秘密。
8. 对测试镜像执行 flatten，比较 layer 数量、manifest 大小和最终 rootfs。
9. 最后使用多阶段构建和 secret mount 重写 Dockerfile，从源头解决问题。

实验时应使用专用目录和测试凭据，不要对不可信镜像执行其中的程序。

## 6. 一句话总结

```text
Manifest 决定使用哪些 layer，
OverlayFS 决定这些 layer 怎样呈现为 rootfs，
容器运行时在 rootfs 上增加隔离、挂载和进程，
Squash 与多阶段构建则解决历史层浪费和敏感内容问题。
```
