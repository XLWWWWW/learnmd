# 提取容器镜像的根文件系统

> 专题导航：[容器镜像文件系统专题索引](./容器镜像文件系统专题索引.md)

本文整理自 Ivan Velichko 的《How To Extract Container Image Filesystem Using Docker》，并补充命令选择、清理方式、多平台镜像和数据保真等实践细节。

## 1. 文章在解决什么问题

容器镜像在存储和分发时由 config、manifest 和多个增量 layer 组成，但开发者通常真正想查看的是：

> 如果用这个镜像创建容器，所有 layer 叠加完成后，最终会得到怎样的一棵根文件系统（rootfs）？

例如，我们希望在不执行镜像内程序的前提下查看：

```text
/etc/os-release
/usr/bin 下有哪些程序
应用配置和静态资源放在哪里
镜像中是否误打包了密钥或调试文件
```

这和“导出镜像本身”不是一回事：

```text
docker save   -> 保存镜像的分层存储与元数据
docker export -> 保存某个容器合并后的文件系统视图
```

镜像 layer、manifest、config 的结构可继续阅读 [容器镜像内部结构详解](./容器镜像内部结构详解.md) 和 [OCI Image Layout 与容器镜像结构](./OCI_Image_Layout与镜像结构.md)。

---

## 2. 方法对比

| 方法 | 是否启动容器 | 得到最终 rootfs | 是否可能混入容器工件 | 适合场景 |
| :--- | :---: | :---: | :---: | :--- |
| `docker save` | 否 | 否 | 否 | 研究镜像层、manifest，或迁移镜像 |
| `docker run` + `docker export` | 是 | 是 | 是，而且应用可能修改文件 | 通常不建议只为查看镜像而使用 |
| `docker create` + `docker export` | 否 | 是 | 少量可能 | 日常快速提取，兼容性好 |
| `docker build --output` | 否（本例无 `RUN`） | 是 | 基本没有 | 更准确地取得镜像原始 rootfs |
| `ctr images mount` | 否 | 是 | 基本没有 | 熟悉 containerd、需要直接挂载时 |

最实用的选择是：

1. 普通排查优先使用 `docker create` + `docker export`。
2. 需要尽量接近镜像原始内容时，优先使用 BuildKit 的 `docker build --output`。
3. 只想读取一两个文件时，不必完整导出，使用 `docker cp` 更方便。
4. 想研究 layer 和镜像元数据时才使用 `docker save`。

## 3. 为什么 `docker save` 不合适

```bash
docker save nginx:alpine -o nginx-image.tar
```

`docker save` 导出的是镜像的存储表示。归档中通常包含镜像配置、manifest 和若干独立的 layer，而不是已经合并好的普通 Linux 根目录。

镜像层表达的是累计变化：

```text
layer 1：增加 /etc/a
layer 2：修改 /etc/a，增加 /app
layer 3：通过 whiteout 删除某些下层文件
```

要从 `docker save` 的结果还原 rootfs，需要按正确顺序应用各层，并正确处理 whiteout、opaque directory、权限、硬链接和扩展属性。这能帮助理解镜像内部结构，但不是日常查看最终文件系统的捷径。

---

## 4. 推荐方法：`docker create` + `docker export`

`docker run` 可以粗略理解成：

```text
docker create + docker start
```

`docker create` 会创建容器及其可写层、准备合并后的 rootfs，但不会启动容器主进程。因此可以用 `docker export` 导出这个尚未启动的容器：

```bash
image='nginx:alpine'
destination='./nginx-rootfs'

mkdir -p "$destination"
container_id=$(docker create "$image")
trap 'docker rm -f "$container_id" >/dev/null 2>&1' EXIT

docker export "$container_id" | tar -x -C "$destination"
```

这种方式比 `docker run` 更安全、更稳定，因为：

- 不执行镜像中的入口程序和启动脚本。
- 不会因为启动逻辑缓慢、崩溃或永久阻塞而影响导出。
- 避免应用启动后改写配置、生成缓存或写入日志。
- 不需要镜像中的程序能够在当前 CPU 架构上运行。

不过，`docker create` 仍然是在创建一个容器。Docker 可能为容器准备 `/etc/hosts` 等运行时内容、挂载点或卷，因此导出的结果不一定与镜像 layer 合并结果逐字节相同。

### 4.1 先保存 tar，再按需解压

```bash
container_id=$(docker create nginx:alpine)
docker export "$container_id" -o nginx-rootfs.tar
docker rm "$container_id"
```

注意：`docker export -o nginx.tar.gz` 不会仅凭扩展名自动 gzip 压缩，文件实质上仍可能是普通 tar。需要压缩时应显式使用压缩工具：

```bash
docker export "$container_id" | gzip > nginx-rootfs.tar.gz
```

### 4.2 只读取个别文件

如果只需要检查一个文件或目录，可以从未运行的容器中直接复制：

```bash
container_id=$(docker create nginx:alpine)
docker cp "$container_id":/etc/os-release ./os-release
docker rm "$container_id"
```

这样无需展开完整 rootfs。

### 4.3 指定多平台镜像的平台

一个 tag 可能同时包含 amd64、arm64 等多个平台。需要明确分析目标平台时：

```bash
container_id=$(docker create --platform linux/amd64 nginx:alpine)
```

如果本地尚无对应平台的镜像内容，Docker 仍需要先拉取它。

## 5. 更准确的方法：BuildKit `--output`

BuildKit 可以把一次构建的最终文件系统直接输出到本地目录。Dockerfile 只有一条 `FROM`，因此这里只继承目标镜像的文件系统，不执行 `RUN`：

```bash
mkdir -p rootfs

docker build --output type=local,dest=rootfs - <<'EOF'
FROM nginx:alpine
EOF
```

老版本 Docker 可能需要显式启用 BuildKit，或者改用 `docker buildx build`：

```bash
DOCKER_BUILDKIT=1 docker build --output type=local,dest=rootfs .
```

这比 `docker create` + `docker export` 更接近“只合并镜像 layer 后的原始 rootfs”，不会引入同等程度的容器创建工件。

需要留意：

- `--output` 依赖 BuildKit。
- `type=local` 输出时的属主映射可能受 BuildKit 运行方式和宿主环境影响；若审计 UID/GID，需单独验证。
- 多平台镜像应通过 `--platform` 指定目标，例如 `docker build --platform linux/amd64 ...`。
- 目标目录应为空或专门用于本次导出，避免旧文件与新结果混在一起。

## 6. containerd 方法：`ctr images mount`

如果宿主机直接使用 containerd，可以将镜像 rootfs 挂载到本地目录，而不创建 Docker 容器：

```bash
sudo ctr images pull docker.io/library/nginx:alpine
sudo mkdir -p /mnt/nginx-rootfs
sudo ctr images mount docker.io/library/nginx:alpine /mnt/nginx-rootfs
```

查看完成后卸载：

```bash
sudo ctr images unmount /mnt/nginx-rootfs
```

不同 containerd 版本的 `ctr` 命令和 snapshotter 支持可能有差异，应以本机的 `ctr images mount --help` 为准。

还要注意 Docker 与 containerd 的命名空间和镜像存储是否共享。即使 Docker 已经拉取镜像，`ctr` 也不一定能直接看到；使用 Docker 管理的 containerd 存储时，常见命名空间是 `moby`：

```bash
sudo ctr --namespace moby images list
```

能否复用 Docker 已拉取的镜像，取决于 Docker 版本、当前镜像存储后端和 namespace，不能只根据“机器上运行着 containerd”作判断。

## 7. 保留权限、属主和扩展属性

如果先导出 tar 再解压，普通用户解压可能改变文件属主、权限，或丢失 capabilities、SELinux 标签等扩展属性。需要尽量保真时可使用：

```bash
sudo tar -xf nginx-rootfs.tar \
  --numeric-owner \
  --same-permissions \
  --xattrs \
  --xattrs-include='*' \
  -C rootfs
```

几点限制：

- 必须有足够权限才能恢复其他 UID/GID、特殊权限和扩展属性。
- macOS、Linux 以及不同文件系统对扩展属性、设备文件和 capabilities 的支持不同。
- rootless Docker、用户命名空间和 BuildKit 可能进行 UID/GID 映射。
- `docker export` 不导出卷中的内容。镜像声明了 `VOLUME` 时，应额外确认对应目录是否符合预期。

因此，如果用途是安全取证、镜像签名验证或逐字节复现，仅把 rootfs 解压到普通目录并不充分，还需要保留原始镜像对象并校验 digest。

## 8. 安全与分析建议

不启动容器不等于完全没有风险。提取不可信镜像时仍应注意：

- 在专用空目录中解压，不要覆盖宿主机系统目录。
- 不要直接执行提取出来的二进制、脚本或安装钩子。
- 不要盲目跟随指向 rootfs 外部的符号链接。
- 用普通用户做静态浏览；只有确实需要恢复属主和扩展属性时才使用特权。
- 大镜像可能占用数倍于压缩镜像大小的磁盘空间。
- 检查密钥和敏感文件时还要分析历史 layers；最终 rootfs 中已删除的文件，仍可能留在较早 layer 中。

最后一点尤其重要：

```text
导出的最终 rootfs 适合回答“容器启动前能看到什么”；
逐层分析镜像适合回答“镜像构建历史中曾经包含过什么”。
```

## 9. 总结

这篇博客最重要的不是记住某条命令，而是分清三个对象：

```text
镜像存储格式：manifest + config + layers
容器 rootfs：各层叠加后，再加一个容器可写层
运行中容器：rootfs + 运行时挂载 + 进程产生的修改
```

因此：

- `docker save` 保存镜像，不直接给出合并后的 rootfs。
- `docker export` 导出容器文件系统，不能直接接收镜像名。
- `docker create` + `docker export` 无需启动进程，是最通用的提取方案。
- BuildKit `docker build --output` 更适合获取少受容器创建过程影响的 rootfs。
- `ctr images mount` 是 containerd 环境中的直接挂载方案。
- 若关心权限、卷、特定平台或历史层中的秘密文件，还需要额外验证，不能只看导出目录。
